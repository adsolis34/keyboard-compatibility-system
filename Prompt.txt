The system is called:

Keyboard Compatibility System

High-level purpose:
The Keyboard Compatibility System helps custom keyboard builders search for keyboard parts, select parts for a build, verify compatibility between selected parts, view trusted compatibility evidence, and handle incompatible or uncertain part selections.

The prototype should be an MVP, not a full production application. Focus on implementing the core use cases clearly and correctly.

Important corrected design logic:
The system flow should be:
1. The user starts or works on a keyboard build.
2. The user selects a keyboard layout and/or preferences.
3. The user searches for parts.
4. The user selects/adds a part to the build.
5. The system verifies compatibility.
6. If compatible, the part can be added.
7. If incompatible, the system should warn the user and suggest recovery.
8. If the part is a group-buy/preorder component, the system should show uncertainty and trusted source information.

Do NOT treat “Search for Parts” as being included inside “Verify Part Compatibility.” Search happens before verification. Verification happens after the user selects or adds a part.

Core use cases to implement:
1. Search for Parts
   - User can search or filter keyboard parts.
   - Parts should include categories such as case, PCB, plate, switches, and keycaps.
   - Results should display useful information like name, brand, category, layout support, version, and compatibility indicators.
   - If no results are found, show a clear no-results message and suggest broadening the search.

2. Add Part to Build
   - User can select a part from search results.
   - The selected part is checked against the current build before being added.
   - If compatible, add it to the current build summary.
   - If a part of the same category already exists, allow replacing it.

3. Verify Part Compatibility
   - System checks whether the selected part is compatible with the current build.
   - Compatibility should consider at least:
     - keyboard layout, such as 60%, 65%, TKL
     - component category
     - mount type or version when available
     - group-buy uncertainty when available
   - The system should return a compatibility result with:
     - status: compatible, incompatible, conditional, or uncertain
     - confidence level
     - explanation

4. Handle Incompatible Part
   - If compatibility fails, display a warning message.
   - Explain why the selected part is incompatible.
   - Suggest compatible alternatives if possible.
   - Allow the user to remove, replace, or choose a different part.

5. View Trusted Compatibility Information
   - Compatibility results should be connected to source references.
   - Show source/evidence information such as source type, title, and trust level.
   - This does not need to use real external data. Use local mock data.

6. Evaluate Group-Buy Component
   - Group-buy or preorder parts may have incomplete specifications.
   - If a group-buy part is selected, show that compatibility may be uncertain or conditional.
   - Display trusted source references when available.
   - Allow the user to include it with a warning or choose another part.

The class design should follow an MVC-oriented object-oriented structure, but do not overcomplicate the prototype.

Important model classes:

- Part
- GroupBuyPart extends Part
- CompatibilityResult

Important controller/support classes:
- BuildController
- SearchController

The GUI/wireframes represent the View layer, so full View classes are optional in code. The implementation can use React components as views.

Expected class/object responsibilities:
User:
- can create or view builds

Build:
- stores selected layout
- stores desired sound profile and typing feel
- stores selected parts
- stores compatibility results
- has methods like addPart, removePart, updateLayout

Layout:
- stores layout name and size
- helps determine whether a part matches the build layout

Part:
- stores part data such as name, brand, component type, layout support, version, mount type, and specs

GroupBuyPart:
- extends or specializes Part
- includes estimated release date, preliminary specs, preorder/group-buy status, and incomplete data handling

CompatibilityResult:
- stores status, confidence level, explanation, and connected source references

SourceReference:
- stores source type, title, trust level, and short description/evidence

BuildController:
- starts a new build
- selects layout
- adds a part to the build
- saves/submits the build

SearchController:
- searches parts
- filters by category, layout, brand, or text query

CompatibilityController:
- verifies part compatibility
- handles incompatible part results

PartCatalog:
- stores and returns local mock part data

CompatibilityEngine:
- applies compatibility rules and returns a CompatibilityResult

SourceReferenceRepository:
- returns mock source references for a part or compatibility result
